# lean-verify v1：实现后的精简验证

测试是一种压缩：用尽量少的代码，证明真正重要的行为没坏。测试不是越多越严谨——每一行测试都要维护、要跑、要读。

## 核心问题

写每个测试前问：**删掉它，会有什么 bug 漏到线上？** 说不出具体的 bug，就不写。

## 顺序

先实现，再验证。不写先行测试；例外只有修 bug（见 diagnosing-bugs）。实现完：

1. 跑全量。被本次改动弄红的旧测试 = 高层已覆盖的行为，先改它们。契约有意变了就逐条改断言，严格程度不降，理由记进「提交前」的表
2. 列计划表：打算写的测试｜防什么 bug｜估计行数。对照「预算」过一遍再动手写 ∵ 先写全再砍是白写
3. 改的是已有行为时，每条留下的测试在旧代码上跑一次，应当断言失败（实现没提交时 `git stash push -- <实现文件>`，跑完 `git stash pop`）。没失败的删掉，或写明防的是将来哪种写错

## 测什么

| 类 | 例子 | 为什么值得 |
|---|---|---|
| 难回退的边界 | 数据 schema、对外接口、跨团队契约 | 一旦坏了，多方要一起改 |
| 修过的 bug | 每个修复一个回归测试 | 已经证明会出错 |
| 人眼看不出的错 | 数值计算、并发、权限 | 看起来对，其实错 |

不测：类型检查能拦住的 ・ 简单 getter、透传、配置 ・ 内部实现细节和私有函数 ・ 第三方库本身 ・ 在更高层测试里已经被覆盖的。

## 怎么测

- **最高的 seam**：在对外接口上测行为，不测内部。理想情况一个功能只有一个 seam
- **不变量优先于枚举**：与其为 20 种输入写 20 个测试，不如在一份真实样本上跑完整流程，断言几条必须永远成立的规则
- **新旧对拍**：性能、缓存、重构这类不该改变行为的改动，在同一份真实样本上跑新旧两版，输出逐字节一致就是证据，一般不用再写单测。旧版用 `git archive <基线提交> <目录> | tar -x -C <临时目录>` 导出
- **表驱动**：确实要多个用例时，写成一张输入/期望表，不复制粘贴测试函数
- **期望值来自独立来源**：已知正确的字面量、spec、真实样本，不用和代码一样的算法重算
- **LLM 行为用评测集，不用单元测试**：模型输出的质量跑样本、看分布和指标；单元测试只管确定性的部分

## 预算

- 默认：测试代码不超过本次实现代码的一半。超出时先停下，说明哪几条为什么值得，让用户确认
- 全套测试应该能在几十秒内跑完；慢的评测集单独跑，不进每次提交
- 用户可以在项目里覆盖这个比例

## 提交前

列一张表给用户，而不是只报「N 个测试通过」：

| 测试 | 防的是什么 bug | 旧代码上 | 行数 |
|---|---|---|---|

「旧代码上」填 红，或 绿 + 防的是将来哪种写错；用对拍代替单测的，写样本和结果。表下列出改过的旧断言和理由。

同时检查已有测试：本次改动让哪些旧测试变得重复或永远不会失败，建议删掉，由用户确认。

## 反模式（来自 tdd，保留）

- 耦合实现：mock 内部协作者、测私有方法、绕过接口直接查数据库。特征：行为没变，重构后测试却挂了
- 同义反复：期望值用和代码一样的方式算出来，永远不会失败；「顺序」第 3 步在旧代码上跑一次就能发现
- 为覆盖率而写：只为了让某一行被执行到，而不是为了拦住某个 bug

## 自我改进

用户指出流程本身的问题时，记进 `lean-verify-改进日志.md`：阶段 ・ 现象 ・ 根因 ・ 改法 ・ 级 ・ 状态，位置按用户的记忆或全局指令，都没写就问。不当场改 skill，攒一批再改。
