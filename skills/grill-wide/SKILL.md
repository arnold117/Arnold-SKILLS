# grill-wide v1：先广后深的追问

目的：帮用户把一个方案想清楚，只在真正重要的地方用力，最后产出收件人能直接用的文档。
默认运行在能读代码、跑代码的环境（如 Claude Code）。

## 原则

- attention 优先：先定这次为谁、为什么决定，再决定问什么
- 先广后深：先铺开全部分支、排好序，才深挖
- AI coding 时代的成本模型：改起来不到 1 小时的不问；重点问难回退的（数据模型、接口边界、跨团队依赖、迁移、读者要做的决定）
- 逻辑优先于语法：表格 + 符号 + 关键词；完整散文只在最后还原时写
- 先查再问：能从材料、代码、数据库、记录稿里得到的，先去读；便宜就能验证的，先跑一下
- 你已经有把握的，不要假装不确定；被否的选项只进文件，不进对话

## 符号

状态：✓ 已定 ・ ? 待定 ・ ~ 假设未验证 ・ ! 风险 ・ × 有分歧 ・ ◇ AI 自己补的 / 代定的 ・ → 行动或依赖(谁)
关系：⇒ 导致 ・ ≠ 与预期相反 ・ ⊂ 属于 ・ ⟂ 互斥 ・ ∵ 因为

## 产出一：决策文件 `grill-<主题>.md`

每轮只改变化的行，并告诉用户改了哪几行。

```
# <主题>
Query：给谁 ・ 要他做什么决定 ・ 场景

## 底片
| 来源 | 位置 | 已读? | 备注 |

## 分支
| # | 分支 | 候选 | 簇 | 可逆 | 影响 | 级 | 状态 |

## 决定
| 符号 | 项 | 内容(关键词) | 依据(位置) |

## 待问
| # | 问题 | 档 | 推荐 | pro | con | 难度(含改造成本) |

## 待验证
| # | 类(验证假设 / 读现状才能定) | 怎么验 | 影响哪个决定 | 结果 |

## 停车场
| 想法/意外 | 来自 |
```

一个单元格只放一种状态；部分已定的分支拆成子项。术语第一次出现时给一句定义 + 一个例子；定义不出来，说明这个概念要先拆。

## 流程（每个阶段结束由用户确认）

### 0. 收底片，定 query
- 读用户给的材料和相关代码、表结构，填底片表（含是否已读）
- query 不清楚时只问：给谁看、要他决定什么。从上下文推出的 query 标 ◇
- 判断场景，选下方侧重

### 1. 铺分支
- 一次列出全部分支和候选，不展开
- 用底片的其他部分交叉检查（相邻功能、已知风险、会修改同一数据的地方），补漏掉的分支，标 ◇
- 给用户看时，主动指出「最可能还漏掉的 2–3 个」及理由。用户回「看着行」时尤其要做：完整的表会让人默认没漏

### 2. 合并与排序
- 先合并：一旦定了会被同时写进同一个地方的分支，归为一簇，按「决定」而不是按「话题」切
- 再打分：可逆性（易/难）× 影响面（小/大）
  - A = 难回退且影响大 → 深挖
  - B = 一项高 → 批量表
  - C = 都低 → 标「实现时定」
- 给用户确认

### 3. 深挖 A 级
- 问之前先查：现状能读到的先读，一两分钟能验证的先跑
- 每个问题先定档：
  - 代定：你有把握且可逆 → 不问，直接定，写进决定表标 ◇，门槛处批量审
  - 确认：你有把握但难逆 → 一行推荐 + 一行理由，pro / con / 难度各一行，用户答是或否
  - 抉择：你真不确定，或取决于用户的价值判断 → 才列完整选项
- 难度必须包含改造现有系统的成本，不只是从零做的成本
- 一次问一个；每个分支最多追两层，然后回全局
- 用户的新想法和目的之外的发现放进停车场

### 4. B 级批量
- 先用 A 级的决定重扫 B 级，已被顺带解决的直接标 ✓
- 剩下的合成一张表：每行一个推荐，用户逐条勾选或改
- 用户回「看着行」时，指出你最没把握的 1–2 行

### 5. 门槛
- 列出所有 ◇、~、→ 依赖和仍是 ? 的项，用户逐类确认
- 给出一张「先定 vs 直接开发」视图：哪些必须先定及原因（改了要谁一起动），哪些可以边做边调。方便在「先开发再说」的团队里沟通
- 门槛前不写代码、不写测试、不写正文

### 6. 靶向还原
- 按决定表写给收件人的文档，内容从底片取，不凭关键词发挥
- 收件人不止一类时，开头放导读：你是谁 → 看哪一节；每类读者一节
- 工程读者要具体字段名、类型、约束；在能读代码的环境里，直接对齐现有命名和表结构
- 仍未验证的内容在文档里明确标出，不写得像已定

### 7. 收件人视角 review
- 对每类收件人做一次冷读。最好由一个没参与前面讨论的子 agent 来做：只给它成稿和读者身份（角色、负责什么、最在意什么）
- 让它以该读者身份列出：拿到后最先问的 3 个问题 ・ 看不懂的术语 ・ 需要自己去翻代码或问人才能补全的地方 ・ 他会反对的地方
- 每条处理成三种之一：补进文档 / 写成明确的待验证项 / 放进开放问题
- 把 review 发现和处理结果一起给用户看，再交付

## 场景侧重

| 场景 | 重点问 | 不问 |
|---|---|---|
| 代码/系统设计 | 数据放哪、接口和边界、跨团队依赖、迁移与回退、谁实现 | 命名、普通边界情况、错误处理、测试细节 |
| proposal/spec | 读者是谁、要他决定什么、最强反驳、谁执行谁依赖谁、本期不做什么 | 措辞、排版、背景铺陈 |
| 调研/读论文 | 这次的目的、比较维度(表的列)、可信度标准 | 与目的无关的方法细节 |
| 会议准备 | 要当场决定的问题、谁必须在、会前要对齐的依赖 | 会上可以再讨论的细节 |

proposal/spec 可在第 1 步后加镜头：决策者、执行者、反对者，各补一张表。

## 停止条件

- 用户喊停
- A 级没有 ? 了
- 确认和抉择档的问题达到约 10 个：停下，汇报剩余 ? 的级别，让用户决定是否继续

## 自我改进

用户指出流程本身的问题时（不是方案的问题），记进 `grill-wide-改进日志.md`：阶段 ・ 现象 ・ 根因 ・ 改法 ・ 级 ・ 状态。不当场改 skill，跑完一整轮后再批量改。
