# build-wide v1.1：把实现票做出来（未经实战）

票来自 `arnold-skills:map-wide` 拆好的实现票：地图上没有 `Type:`、带 `ready-for-agent` 的票。票放在哪、怎么关，看 `docs/agents/issue-tracker.md`。

## 两种用法

| 用法 | 输入 | 怎么做 |
|---|---|---|
| 一张票 | 一张实现票 | 当前会话按「做一张票」走完 |
| 一批票 | 一张地图 | 父会话调度；每张票派一个子 agent 按「做一张票」的前四步走，审查、提交、合入由父会话做 |

两种用法都一样：主线外顺手修的支线，开工前写明停点（默认一轮审查后只修挡上线的，其余进汇报的「不做」表）∵ 审查一轮冒一个新问题，没有停点就会一直追下去

## 做一张票

| 步 | 做什么 |
|---|---|
| 1 开始 | 从票务系统取票，报标题；先认领。一张票时：先 fetch，从最新主线开分支（规则按仓库约定）。读票要碰的代码现状 |
| 2 实现 | 先实现，不写先行测试；常跑类型检查和相关测试文件；现有测试、回归闸、契约测试、红线扫描照跑 |
| 3 验证 | 调 `arnold-skills:lean-verify` 补最少的测试，列表：每个测试防什么 bug |
| 4 全量 | 跑全量；红了先和主线对比 ∵ 主线上本来就红的不算这次的 |
| 5 审查 | 按下方「审查」做，起点 = 这张票的分支从主线分出的地方。修完再跑全量 |
| 6 提交 | 提交到当前分支；推不推、怎么合入等用户定。推就走 PR，不直推主线，不推半成品。报告带前后对比：测试数、代码行数，涨了说涨了；没做的列一张表：不做 ｜ 理由 ｜ 什么时候再做 |

## 一批票

| 谁 | 做 | 不做 |
|---|---|---|
| 父会话 | 派工、认领、写 brief、合入、跑全量、解冲突、登记、收尾审查 | 不把判断类的活下放 |
| 子 agent | 在自己的 worktree 里走「做一张票」第 2–4 步 | 不碰主工作树、不推送、不碰票 / 地图 / 共享登记文件 |

- 每次派子 agent 显式写 `model: sonnet`，不派 Opus；汇报里写明模型
- 子 agent 交回的东西要复核，不直接信

1. 读地图、spec 和实现票，理清阻塞关系
2. 可选：派一个只读子 agent 看要碰的代码或文档，笔记写到仓库外，后面的子 agent 都能读
3. 先 fetch，从最新主线开集成分支和它的 worktree；分支起有意义的名字（如 `wt/<功能>`、`wt/<功能>-t<N>`），不用工具自动生成的
4. 派工看改动的文件相不相交，不看票号：不相交的马上并行；相交的等前一张合入后，从最新集成分支再开。派之前由父会话认领
5. brief 固定写明：
   - 先确认 worktree 基于集成分支，不是就 `git merge --ff-only <集成分支>` ∵ 工具开的 worktree 默认从主线分出
   - 前一张票刚改过的文件，先 `git log -N --stat` 看一眼
   - 改动前后各跑一次全量，报数
   - 测试替身的名字不能和真实的策略、函数撞名
6. 合入只由父会话做：rebase → 跑这张票的目标测试 → `merge --ff-only` → 跑全量 → 删 worktree 和分支 ∵ 两边各自全绿 ≠ 合并后测试还在测东西。冲突一般只在文档里：每一行取改它的那张票的版本，不手工糊
7. 合入后可以开工的票变了 ⇒ 接着派
8. 全部合入后：全量（和主线对比）→ 审查（按下方「审查」，起点 = 集成分支从主线分出的地方）→ 派一个子 agent 修 → 父会话自己再跑一次全量
9. 父会话统一回填：票的状态和答案、地图、登记文件、记忆；先看仓库约定（.gitignore、哪些文件不提交）再决定入不入库
10. 汇报：每一波派了几个子 agent、什么模型；前后对比表（测试数、代码行数；冗余和体量分开列）；没做的列表同「做一张票」第 6 步。推不推、怎么合入等用户定
11. 清理所有 worktree

! 几个 worktree 并行跑全量时，共用的临时目录会偶尔踩出假红：单独重跑一遍确认

## 审查

改动 = `git diff <起点>...HEAD` 加 `git log <起点>..HEAD --oneline`；先确认起点存在、改动不为空，再派人。两个子 agent（`model: sonnet`）同时派，各审一个方向，互不看对方：

| 方向 | 给它 | 要它报（400 字以内） |
|---|---|---|
| 规范 | 改动 + 仓库里所有写了代码规范的文件（CLAUDE.md、AGENTS.md、CONTRIBUTING.md 等）+ 下面的坏味道清单 | 违反哪条规范：引文件和条目 ・ 看到的坏味道：说名字、引代码。规范是硬的，坏味道只是提醒；仓库规范允许的不报，工具已经管的不报 |
| spec | 改动 + 这张票 + 对应的 spec 故事 | 漏做或只做一半的 ・ 没要求却做了的 ・ 看着做了但做错的；每条引 spec 原句。「待评估」「对接时再定的细节」不算缺漏。没有 spec 就不派，报告里写明 |

坏味道清单（Fowler《重构》第 3 章，仓库没写规范也照用）：名字看不出意思 ・ 重复代码 ・ 依恋情结（总在用别处的数据）・ 数据泥团（几个字段总一起出现）・ 基本类型偏执（该有自己类型的概念拿字符串顶着）・ 重复的条件分支 ・ 霰弹式修改（一个改动散到很多文件）・ 发散式变化（一个文件因不相干的原因被改）・ 夸夸其谈通用性（为没有的需求加抽象）・ 过长的调用链 ・ 中间人（只转发的一层）・ 被拒绝的遗赠（子类不用继承来的大部分）

两份报告分开给，不合并、不重排 ∵ 符合规范不代表做对了需求，反过来也一样；末尾一行：每个方向几条、各自最严重的一条。每条带文件行号。父会话复核后先分拣：挡上线的修，其余进汇报的「不做」表，不顺手全修。

## 自我改进

用户指出流程本身的问题时，记进 `build-wide-改进日志.md`：阶段 ・ 现象 ・ 根因 ・ 改法 ・ 级 ・ 状态，位置按用户的记忆或全局指令，都没写就问。不当场改 skill，攒一批再改。
