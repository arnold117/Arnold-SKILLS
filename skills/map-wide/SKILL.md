# map-wide v1.1：给大事画地图（未经实战）

一件事大到一个会话装不下、路还看不清时用。地图上有两种票：**决定票**（要定的事）和**实现票**（要做的事）。map-wide 只定和拆，不写代码；实现票交给 `arnold-skills:build-wide`。

## 原则

- 一次只问一个问题：讨论都走 `arnold-skills:grill-wide`
- 新信息来了先改票：新需求、会议结论先加票或改票，再拿着票讨论；不写方案长文来提问
- 纪要、需求里的具体写法默认是示例 ⇒ 先开 research 票查成熟产品怎么做
- 给人看的地方用票的标题，不用光秃秃的编号
- 一个决定推翻了旧说法 ⇒ 在地图、所有票、spec 里 grep 旧说法，清干净再给用户看

## 地图

存在哪、怎么查、怎么认领：看 `docs/agents/issue-tracker.md` 的「Wayfinding operations」一节；没有就先问用户。

地图是一张带 `wayfinder:map` 标签的票，是索引：决定只写在各自的票里，地图只放一行要点和链接。五节标题保持英文原样 ∵ 看板按标题解析：

```markdown
## Destination
<终点：这张地图要走到哪，一两行>

## Notes
<领域；每次都要用的 skill；长期约定；spec 在哪>

## Decisions so far
- [<已关票的标题>](链接)：<一行要点>

## Not yet specified
<还说不准、暂时拆不成票的问题>

## Out of scope
<不做的：一行一条，写理由，链接已关的票>
```

## 票

| | 决定票 | 实现票 |
|---|---|---|
| 是什么 | 一个要定的问题 | 一条垂直切片：从数据到界面一次打通的一小段功能，能单独演示或验证 |
| 正文 | `## Question` | 要做什么（用户视角）・ 现状 ・ 补到能开工还缺什么 ・ 验收标准。细节指回 spec 的对应故事，不复制 |
| `Type:` | research / prototype / grilling / task | 不写 |
| 标签 | `wayfinder:<类型>` | `ready-for-agent` |
| 谁处理 | map-wide 走地图 | build-wide |

- 字段行（`Status:` `Type:` `Blocked by:` `Labels:`）顶格、不加粗、只写单个值；没有阻塞写 `Blocked by: —` ∵ 看板读不出加粗的字段，空值会吞掉下一行
- 动手前先认领；阻塞用票务系统自带的依赖，阻塞它的票全关了才算解锁
- **可以开工的票** = 打开、已解锁、没人认领
- 答案在解决时写进票，不改问题正文；产出的东西放链接，不贴全文

### 决定票的四种类型

| 类型 | 谁做 | 怎么解决 |
|---|---|---|
| research | agent 自己 | 子 agent（`model: sonnet`）查一手资料（官方文档、源码、规范；每条说法追到拥有它的源头，不引转述），写成一份 Markdown：逐字引用出处，找不到写「未找到」；主控抽查 3–5 条原句。结论放 `research/<名>` 分支（推送，不开 PR），票里放指针 |
| prototype | 和用户一起 | 按下方「原型」做，给用户看了再定 |
| grilling | 和用户一起 | 默认类型。调 `arnold-skills:grill-wide`；词汇表和 ADR 按下方做 |
| task | 能自己做就自己做，否则给用户一张清单 | 做决定前必须先完成的手工活；答案记下做了什么、后面的票要用的事实 |

和用户一起的票只在真实对话里解决，agent 不能替用户回答。grill-wide 用在一张票上：底片 = 地图 + 这张票 + 相关的已关票；决定表写进这张票的答案。

### 原型

- 先在原型开头写下它要回答的问题 ∵ 答错问题的原型白做
- 按问题选形状：
  - 逻辑或状态对不对 ⇒ 一个双击就能打开的 HTML。逻辑写成不碰页面的纯函数，之后能直接搬进代码；每个动作一个按钮，每步后显示完整状态；备几个场景（正常路径、刁钻边界、本该被拒的操作）。全用业务语言，不懂代码的人也能点
  - 界面长什么样 ⇒ 在已有页面上做 3 个结构不同的版本（布局、信息层级不同，不只是换颜色），用 URL 参数切换；没有能挂的页面才另开临时页面
- 一条命令能跑；不写测试、不接真数据库、不打磨
- 定完：结论写进票；验证过的部分搬进正式代码；原型推到 `prototype/<名>` 分支（不进主线），票里放指针

### 词汇表和 ADR

项目已有的沿用它的文件和格式（如 `CONTEXT.md`、`docs/adr/`）；没有就等第一个词定下、第一份 ADR 要写时再建。

- 用户的说法和词汇表或代码对不上 ⇒ 当场指出，问哪个对
- 说法含糊 ⇒ 问清指的是哪个已有概念；只用用户团队已有的词，不造新词
- 用具体场景试概念的边界，尤其是两个相近概念之间
- 词一定下就写进词汇表：一句定义 + 要避免的说法；只放概念，不放实现
- ADR 只在三条都满足时提议：难回退 ・ 没有上下文后来的人会看不懂 ・ 有真的备选、为具体理由选了这个。其余写进决定票的答案就够

## 还说不准的、不做的

- 问题能说准 ⇒ 开票，哪怕暂时被阻塞；说不准 ⇒ 写进 Not yet specified，不提前切成票
- 解决一张票后，看清了的转成新票，并从 Not yet specified 删掉
- 超出终点的 ⇒ 不做：已有的票关掉，在 Out of scope 记一行理由；不进 Decisions so far

## 三种用法

每个会话只解决一张决定票，research 票除外。

### 画地图：用户带着一个模糊的想法来

1. 定终点：用 grill-wide 讨论清楚，定下的词按「词汇表和 ADR」记
2. 铺开：跑 grill-wide 阶段 0–2（收底片、铺分支、合并排序）。A、B 级开决定票，B 级可以几条合成一张；C 级不开票，实现时再定；说不准的进 Not yet specified。铺完发现一个会话就能做完 ⇒ 不需要地图，停下问用户
3. 建地图：填好 Destination 和 Notes
4. 建票：先建出来，第二遍再连阻塞和互相引用 ∵ 要先有编号，不写占位编号
5. 派子 agent 并行解决 research 票；结果攒齐合成一条汇报，只报和当前问题有关的
6. 停：画地图本身就是一个会话的活

### 走地图：用户带着地图来，可以不指定票

1. 读地图，不读所有票的正文
2. 选票：用户指定的那张，否则取可以开工的决定票里排第一的；先认领
3. 按 `Type:` 解决；需要时再读相关票的全文
4. 记录：答案写进票，关票，在 Decisions so far 加一行
5. 更新地图：新冒出的票先建再连；看清了的转成票；超出终点的移进 Out of scope
6. 某个用户故事需要先定的决定都关了 ⇒ 用 grill-wide 第 6–7 步把它写进 spec（spec 在哪记在 Notes），然后按「拆票」拆它。之后有决定改到已写的故事 ⇒ spec 升版，受影响的实现票同步改

### 拆票：spec 里有写好的故事

没有地图就先建一个 `map.md`：Destination = 做完这份 spec，Notes 写 spec 在哪 ∵ 没有 map.md 的票在看板上看不到。

1. 读 spec 和相关代码；有能先重构、让后面更好做的，先拆成一张票
2. 按故事拆实现票：每张一条垂直切片，一个会话装得下
   - 例外：牵一发动全身的机械改动（改列名、改共享类型）拆成「先加新的 → 分批迁过去 → 删旧的」，每批一张票
3. 跟用户确认拆法，一次问一个：粒度 → 阻塞关系 → 要不要合并或拆开
4. 按阻塞顺序建票（被依赖的先建），连好阻塞关系
5. 不关、不改父票

## 自我改进

用户指出流程本身的问题时（不是方案的问题），记进 `map-wide-改进日志.md`：阶段 ・ 现象 ・ 根因 ・ 改法 ・ 级 ・ 状态，位置按用户的记忆或全局指令，都没写就问。不当场改 skill，攒一批再改。
